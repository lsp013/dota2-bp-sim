# Dota 2 BP 模拟器 (dota2-bp-sim)

一个纯静态的 Dota 2 BP 助手：根据当前版本的对位胜率数据，在选人阶段推荐能**克制对方阵容**、同时**契合我方阵容**的英雄。

部署在 GitHub Pages 上，**零服务器、零运维** —— 数据由 GitHub Actions 每周自动刷新一次，手机浏览器打开即用。

---

## 它做什么

输入双方已选英雄 → 输出带依据的推荐：

- **推荐选人**：综合「对敌克制」「与我方协同」「版本强度」三项打分排序
- **点开任意英雄**：看到逐条对位数据（胜率 + 样本量 + 置信标签）
- **点按或拖拽**录入双方英雄，触屏和桌面都可用

三个权重都可在界面上实时调整。

界面布局：上方是双方选人栏，下方左半边是**英雄池**、右半边是**推荐选人**，
两边各自有滚动条，所以再长的列表也不会互相挤走。

---

## 为什么不是"DotaBuff 胜率排序"

单纯按胜率排序在 BP 阶段几乎没用，因为它完全不看你面对的是谁。这个项目做了三件关键的事：

### 1. 用「收缩估计」打分，而不是原始胜率

OpenDota 的对位数据样本量很小（实测 15,972 个组合：中位数 **47 场**）。原始胜率在这种样本下是噪音——2 场全胜就是"100%"。

本项目把观测胜率**向 50% 收缩**：打 n 场的组合保留约 `n/(n+15)` 的优势幅度。

> **这里踩过一个坑，值得记下来。** 最初我用的是**威尔逊 95% 置信下界**当分数。下界是"最坏情况估计"，用来判断样本可不可信是对的，但**当分数就错了**。
>
> 真实案例：冰魂 vs NEC = 22 胜 / 35 场 = **62.9%**，是全数据集里第 5 强的克制关系。但它的下界只有 **0.465**——低于 50%，看起来像个劣势对位。结果引擎把冰魂排到第 16 名、克制项只给 44%，把一个真信号彻底毁掉了。
>
> 改用收缩估计后，冰魂进入前五。
>
> **下界负责「能不能信」，收缩估计负责「值多少分」——两者不能混用。**
>
> 收缩强度 `k` 是一个**取舍**，不是纯数学问题：统计上更保守的做法是取 `k≈50–100`（按对位效应的一般离散度做经验贝叶斯）。
>
> ⚠️ **后来发现我把它调错了方向。** 我曾把 `k` 从 25 调到 15，动机是"让冰魂进入前五"——那是**在向噪音过拟合**。接入 STRATZ 的大样本（冰魂 vs NEC 有 5,208 场，而非 35 场）后才看清：
>
> - OpenDota 里的"头号克制" Shadow Demon（65.0%，40 场）**实际是 47.0%（1,530 场），垫底**
> - Windranger 从 60.5% 变成 47.1%（劣势）
> - 冰魂确实是真克制（54.6%），但**不需要我手动调参让它进榜**
>
> **教训：样本不足时，正确的做法是去拿更多数据，而不是调低先验把它"救"进榜单。** 右下角的数据源开关就是为了这个。

分层策略（阈值来自实测分布，用于显示可信度标签）：

| 样本量 | 标签 | 是否参与排序 |
|---|---|---|
| ≥ 100 场 | 🟢 可靠 | 是 |
| 30–99 场 | 🟡 参考 | 是 |
| < 30 场 | 🔴 样本少 | 否 |

### 2. 每张推荐卡都标出「最克谁」

因为收缩会把小样本的真实优势压平，卡片上额外直接写出**对敌方最强的那一组对位**，例如
`最克 Necrophos 62.9% (35 场)`。这样即使某个英雄因为整体胜率偏低而排名靠后，它针对当前阵容的价值也不会被埋掉。

### 3. 按覆盖率惩罚证据不足的推荐

只对 3 个敌方英雄中的 1 个有数据，和一个对 3 个都有数据，不应等价。**覆盖率 = 有数据的敌人数 / 敌人数**，并按 `覆盖率²` 把分数往 50% 收缩。

平方而非线性是实测调出来的：线性收缩太弱，一个只覆盖 1/2 敌人的英雄仍能保留 50% 的优势，从而压过覆盖率 100% 的英雄（实测 0.58 vs 0.53）。平方后这类英雄会掉到合理位置。

## 数据源：右下角可以切换

界面右下角有 **OpenDota / STRATZ / 合并** 三个按钮，切换后推荐会完全按所选数据重算。

| | OpenDota | STRATZ | 合并 |
|---|---|---|---|
| 单对位样本**中位** | **47 场** | **2,014 场** | 两者相加 |
| 覆盖 | 127 英雄 · 15,972 组 | 127 英雄 · 16,002 组 | 最全 |
| 分段过滤 | ❌ 全分段混合 | ✅ 已校准四个分段 | — |
| 刷新方式 | CI 每周自动 | **手动**（浏览器抓取） | — |
| 文件大小 | 0.34 MB | 0.39 MB | 浏览器内实时合并 |

### 文件格式：只存观测值

每个对位只存两个**实际观测到的整数**：

```json
{ "g": 5208, "w": 2844 }     // 场次、胜场
```

胜率、威尔逊置信区间、可信度标签**全部是这两个数的推导结果**，由 `src/dataset.mjs` 在加载时重算。这**不是有损压缩**——原始计数被逐一原样保留，只是不再把算好的结果也写进文件。

改成这个格式后：

| | 之前 | 现在 |
|---|---|---|
| data.json | 1.04 MB | **0.34 MB**（−67%）|
| data-stratz.json | 1.09 MB | **0.39 MB**（−64%）|
| 启动传输（合并为默认，两个都加载） | 2.13 MB | **0.73 MB**（−66%）|

改格式时我验证过：**15,972 + 16,002 组数据的 `g`/`w` 全部逐一相同（0 处差异）**，重算出的 `p`/`t` 与原文件也完全一致（0 处差异）。旧格式的文件仍然能读——水合是幂等的，会顺手把过期的派生值修正过来。


**这不是可有可无的选项，而是这个工具最关键的一个修正。** 同样问"谁克 NEC"，两个源给出的答案差别巨大：

| 英雄 | OpenDota | STRATZ | 场次 |
|---|---|---|---|
| Shadow Demon | **65.0%（排第 1）** | **47.0%（垫底）** | 40 → 1,530 |
| Windranger | 60.5% | **47.1%（劣势）** | 119 → 7,046 |
| 冰魂 | 62.9% | 54.6% | 35 → 5,208 |
| Muerta | 60.2% | 52.5% | 88 → 5,415 |

**OpenDota 的"头号克制"其实是 47% 的劣势对位。** 40 场样本的噪音足以把排名彻底颠倒——这正是收缩估计想缓解、但 `k=15` 远远不够的问题。STRATZ 的样本量大 15–50 倍，收缩几乎不起作用，数字才靠得住。

`合并` 模式**逐对位把场次与胜场相加**（不是平均百分比），所以大样本自然占主导；它的主要价值是补足两边各自的空白。注意两个源的人群并不相同（OpenDota 是滚动近期＋全分段，STRATZ 是一周＋已校准分段），合并结果应当理解为"我们知道的一切"，而不是一次干净的估计。

### STRATZ 为什么需要手动刷新

`api.stratz.com` 在 **Cloudflare 机器人验证**后面。纯 HTTP 客户端（node / curl / python / **GitHub Actions runner**）拿到的都是 `Just a moment...` 页面——我在本机、在沙箱、以及**关掉 TLS 证书校验之后**都复现了同样的拦截，所以这是客户端指纹问题，不是证书或 IP 问题。**只有真实浏览器能通过。**

因此 STRATZ 数据靠浏览器控制台抓取（见 `scripts/stratz-matrix-snippet.js`），无法进 CI。数据抓取时间会显示在「数据」面板里，超过 21 天会标红提醒。

## 另一个数据源：OpenDota

**免费、无需 API key。**

关键发现：**`/heroes/{id}/matchups` 本身就已经是一个滚动的近期窗口**，不需要自己实现"只保留最近 N 天"。

实测依据：

```
水晶室女 全时段 pub_pick  = 536,319 场
水晶室女 /matchups 总样本 =   9,750 场   ← 仅 1.8%
```

尝试加 `?date=30` 参数**完全无效**（返回同样 9750 条）。所以"只要新版本数据"这件事由 OpenDota 上游自动完成，维护成本为 0。

**但它的单对位样本中位只有 47 场**，这是它最大的弱点——见上面那张对比表。


GitHub Actions 每周一自动跑一次（大版本更新后可手动触发），把 `public/data/data.json` 提交回仓库。

### 运维负担

实际上接近零：

- 无 `npm install`（**零运行时依赖**，只用 Node 内置 `fetch`）
- 数据窗口由 OpenDota 维护，你不需要清理旧数据
- 只有 OpenDota 改接口才需要动代码

## 本地运行

需要 Node ≥ 20。

```bash
npm run fetch     # 抓数据 + 同步 src/ 到 public/lib/（约 3 分钟）
npm run serve     # http://127.0.0.1:8787
npm test          # 跑测试
```

抓数据会比较慢且会偶发 HTTP 429 —— 这是正常的，脚本内置了限速（全局 700ms 间隔 + 指数退避 + 遵守 `Retry-After`）。实测 127/127 英雄全部成功。

若你的环境限制了进程 spawn（某些沙箱），用 `npm run test:direct` 代替 `npm test`。

> **注意 Node 版本**：CI 跑的是 **Node 20**，本地可能是更高版本。
> 曾因此挂过一次构建：`app.js` 里有一句 `navigator.vibrate`，而 Node 20
> **没有全局 `navigator`**，抛 `ReferenceError`；本地的 Node 24 有这个全局，
> 所以本地全绿、CI 全红。
> 改完代码请尽量用 Node 20 验证一次（`nvm use 20`），或保持对浏览器全局量的
> `typeof` 防御写法。`tests/ui.test.mjs` 里有一条专门的回归测试覆盖这个坑。

## 部署到 GitHub Pages

```bash
git init
git add .
git commit -m "initial commit"
git branch -M main
git remote add origin https://github.com/<你的用户名>/dota2-bp-sim.git
git push -u origin main
```

然后到仓库 **Settings → Pages → Build and deployment → Source** 选 **GitHub Actions**。

之后每次 push 会自动构建部署；每周一定时刷新数据。网址：

```
https://<你的用户名>.github.io/dota2-bp-sim/
```

手机上打开后可以「添加到主屏幕」，用起来和 App 一样。

## 操作方式

**点按**：先在上方「加入我方 / 加入敌方」切换目标，再点英雄池中的英雄即可。
（早期版本只能点选我方英雄，敌方只能靠右键——手机上根本没法用，已修。）

**拖拽**：直接把英雄从池子拖到上方的「我方」或「敌方」栏位。

- 拖到横线上会高亮对应的队伍
- 可以把一个已选英雄从一队拖到另一队（自动移动，不会同时存在于两队）
- 把已选英雄拖回英雄池区域 = 移除
- 桌面上拖动即时生效；触屏需要**长按约 0.2 秒**再拖（否则会与页面滚动冲突）

两队各自上限 5 个，满了会抖动提示。

## 项目结构

```
src/
  wilson.mjs         威尔逊置信区间 + 分层阈值（核心统计逻辑）
  recommend.mjs      推荐引擎：打分、覆盖率惩罚、对位查询
  draft.mjs          选人状态规则（每队上限、换边、拖放判定）
  merge.mjs          两个数据源的合并（逐对位相加场次与胜场）
public/
  index.html         页面
  app.js             前端逻辑（BP 状态机、拖拽、数据源切换、渲染）
  styles.css         深色移动优先样式
  data/data.json           OpenDota 数据（由 Actions 每周自动更新）
  data/data-stratz.json    STRATZ 数据（浏览器抓取后由 build-stratz.mjs 生成）
  lib/               由 scripts/sync-lib.mjs 从 src/ 自动生成，勿手改
scripts/
  fetch-data.mjs             OpenDota 抓取管线
  build-stratz.mjs           把浏览器抓来的 STRATZ dump 转成同结构数据集
  slim-dataset.mjs           把旧格式数据集转成精简格式（不重新抓取，不动 g/w）
  stratz-matrix-snippet.js   全英雄矩阵的浏览器控制台脚本（需手动粘贴）
  stratz-browser-snippet.js  单英雄对位探测（NEC 案例用）
  stratz-probe.mjs           Node 版探测（会被 Cloudflare 拦，保留作对照）
  sync-lib.mjs               把 src/ 镜像到 public/lib/ 并重写 import 路径
  serve.mjs                  零依赖本地静态服务器
tests/
  wilson.test.mjs        9 个测试
  dataset.test.mjs       9 个测试（水合：无损、幂等、容错）
  recommend.test.mjs    22 个测试
  draft.test.mjs        18 个测试
  merge.test.mjs        10 个测试
  ui.test.mjs           23 个测试（用自建 DOM 驱动真实的 app.js）
```

`src/` 是唯一真相来源，`public/lib/` 是构建产物（因为 GitHub Pages 只能服务 `public/`）。

「英雄池」和「推荐选人」两个面板各自有独立滚动条（最大高度 `min(70vh, 620px)`，
窄屏分别 50vh / 46vh），所以两边都不会被对方的长列表挤出屏幕。

合计 **91 个测试**，在 Node 20.20.2（CI 同版本）与 Node 24 上全绿。
`tests/ui.test.mjs` 用一份手写的迷你 DOM 驱动真实的 `app.js`，
因此能覆盖"点选敌方英雄"、"点击不被拖拽逻辑吞掉"、"拖拽换边"、"切换数据源"
这类只有交互层才会暴露的 bug。

## 打分模型

```
对敌项 = 对敌方所用英雄的合并胜场/场次，再向 50% 收缩（k=15）
协同项 = 对我方所用英雄的合并胜场/场次，再向 50% 收缩（k=15）
版本项 = 该英雄全对位汇总胜率，同样收缩

总分 = (0.7·对敌项 + 0.2·协同项 + 0.1·版本项)   // 权重可在界面实时调
       其中对敌项再按 覆盖率² 向 0.5 收缩
```

**为什么「克制」占 70%**：这个工具回答的是"面对对方这套阵容我该选什么"，具体对位才是重点。而"版本强度"是全局胜率，信息量分散、且与对位矩阵高度重叠（它本来就是同一批对位汇总出来的）。早先按 50/30/20 配比时，它会系统性地埋掉那些**整体胜率低但对位极强**的英雄——冰魂整体只有 47.9%，打 NEC 却有 62.9%，在旧权重下只能排第 9。

留 10% 给版本强度而不是直接删掉，是因为"选一个整体很弱的英雄"本身确实有代价。

三个滑杆可以随时改这个配比；把「克制」拉到 100% 就是纯对位排序。

## 已知局限（重要，请务必阅读）

### 1. 对位数据不区分分路 —— 这是最大的问题

「敌法 vs 美杜莎」这类数据的样本，**绝大多数来自两人并未同路对线的对局**。它反映的是"选了该英雄的队伍是否获胜"，而不是严格的对线克制关系。

实测这个具体例子：

```
敌法 vs 美杜莎： 胜率 46.8%，仅 47 场
美杜莎 vs 敌法： 胜率 53.2%
```

也就是说，**"敌法克制美杜莎"这个广为流传的说法，在数据里并不成立**，而且样本量根本不足以支撑任何结论。

### 2. 选择偏差

玩家倾向于在**认为能赢时**才选某些英雄。因此对位胜率里混入了"人类已有认知"，而不纯是英雄属性。

### 3. 协同项是启发式近似

OpenDota 公开接口**不提供"同队胜率"**，所以「协同」用的是对位数据的补集作为代理——它衡量的是"这两个英雄互相之间的纪录"，是共现代理，不是真正测得的同队协同。

要做真正的协同项，需要解析 replay 数据（OpenDota 的 `/parsed_matches` 或自建解析管线），那是另一个量级的工程。

### 4. 只有二阶交互

真实阵容强度是三阶效应（控制 + 爆发 + 推进）。本项目只能观测两两关系，无法建模"三人组合"。

### 5. 分段差异 —— 部分已解决

OpenDota 的数据不区分天梯分段，冠绝局与先锋局的克制关系可能完全不同。

**STRATZ 有分段过滤**（`bracketBasicIds`：HERALD_GUARDIAN / CRUSADER_ARCHON /
LEGEND_ANCIENT / DIVINE_IMMORTAL），当前抓取的是这四段合并。分段之间的差别是真实的，例如打 NEC 的高分克制榜：

| 分段 | 头名 | 冰魂 |
|---|---|---|
| 神圣/不朽（高分局） | Medusa 63.5%（219 场） | #9 |
| 传奇/远古（中高分局） | Leshrac 56.9%（778 场） | #9 |

注意 **Medusa 在高分局对 NEC 有 63.5%**——这提醒我们分路外的克制关系（美杜莎的魔法盾让她扛得住 NEC 的消耗）也能很强。若要按自己分段看，需要重新抓一次指定 `bracketBasicIds` 的数据。

### 6. STRATZ 数据会过期

它无法进 CI（Cloudflare），只能手动抓。面板里会显示抓取时间，超过 21 天标红。当前版本除非你重新跑浏览器脚本，否则会一直停在抓取那一天。

## 建议用法

把它当作**提供证据的参谋**，不是替你决策的司令：

- 看推荐时**先看样本量标签**，🟡 和 🔴 的要自己判断
- 结合自己的英雄池和队伍体系 —— 这些数据里没有
- 对方队伍的 BP 习惯、选手擅长英雄，同样不在数据里
- 遇到反直觉的数据（比如上面敌法 vs 美杜莎），那通常意味着**该重新审视自己的直觉**，而不是工具错了
